## 一、requests.http 追加四个请求

```
### 12.1 分页查订单（第0页每页2条，倒序——最新在前）
GET http://localhost:8080/order/list?page=0&size=2

### 12.2 订单详情（id 换成你实际有的订单号）
GET http://localhost:8080/order/1

### 12.3 查不存在的订单（预期 code=40402）
GET http://localhost:8080/order/999

### 12.4 按菜名查订单：谁点过回锅肉（JPQL 联表）
GET http://localhost:8080/order/search?dish=回锅肉
```

## 二、验证清单（全过才算下课）

**0. 先造数据**：重放 2.2 下三单（此时 `kitchen-failure` 必须是 false）。

**1. 发送 12.1 分页查询**

预期（3 条订单、每页 2 条 → 总页数 2；records 按下单时间**倒序**，最新订单排第一）：

```json
{"code":200,"data":{"pageNum":0,"pageSize":2,"records":[{"itemList":[...],"orderId":3,...},{"itemList":[...],"orderId":2,...}],"totalElements":3,"totalPages":2},"msg":"操作成功"}
```

（orderId 具体数值取决于你今天累计下了几单；把 `page=1` 再发一次，应返回剩下的 1 条——翻页成功。）

同时看终端 SQL **三连**（本课的透视眼时刻）：

```
Hibernate: select ... from t_order o1_0 order by o1_0.create_time desc offset ? rows fetch first ? rows only
Hibernate: select count(o1_0.id) from t_order o1_0
```

——倒序排序 + `offset/fetch` 翻页 + `count` 算总数，全部自动生成。你一行 SQL 都没写。

**2. 发送 12.2 订单详情** → 正常返回该订单的 VO（orderId/itemList/totalMoney）。

**3. 发送 12.3 查不存在的订单** → `{"code":40402,"data":null,"msg":"该订单不存在"}`——第 6 课的处理台 + 今天的错误码无缝衔接。

**4. 发送 12.4 按菜名搜索**

预期：命中所有点过回锅肉的订单（刚才 3 单如果都是 2.2 的组合，应该返回 3 条）。终端能看到联表 SQL：

```
Hibernate: select distinct o1_0.id,... from t_order o1_0 join t_order_item oi1_0 on o1_0.id=oi1_0.order_id where oi1_0.dish_name=?
```

——你写的 JPQL 被 Hibernate 翻译成了带 join 的真 SQL。对照第 9 课画的"两本账"，外键 `order_id` 就是那条缝。

**5. 浏览器**：点餐页点"📖 翻账本"——最近 5 笔订单的 JSON 出现在账本区。前端第三次进化完成。

## 四、课后练习

1. **课后主作业——时间范围过滤**：老板想看"今天下午的订单"。给 `OrderRepository` 加方法名派生查询 `Page<Order> findByCreateTimeBetween(LocalDateTime start, LocalDateTime end, Pageable pageable)`（第 8 课讲过派生规则：Between = 闭区间），Service/Controller 各加一层，试试查"从一小时前到现在"。（提示：`LocalDateTime.now().minusHours(1)`。）
2. **排序自由练**：把 12.1 的排序从 createTime 倒序改成 `totalAmount` 从大到小——最贵订单排第一。翻页结果变了吗？
3. **思考题**：页码从 0 开始 vs 从 1 开始，为什么程序员偏爱 0？（提示：`offset = page * size` 这个公式如果 page 从 1 开始要怎么改？）以及：为什么 JPA 明明已经查了数据，还要**多花一条** count SQL？不查行不行？

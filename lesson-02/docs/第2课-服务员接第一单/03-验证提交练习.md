# 第2课 · 验证、提交与练习

## 一、requests.http 长出三个新请求

打开项目根目录的 `requests.http`，在末尾追加三个请求（POST 请求的格式注意：请求行下面一行写 `Content-Type`，空一行，再写 JSON 请求体）：

```
### 2.1 查菜单（预期 6 道菜）
GET http://localhost:8080/menu

### 2.2 正常点单：回锅肉x2 + 米饭x2（预期 totalMoney=38）
POST http://localhost:8080/order
Content-Type: application/json

{
  "dishList": [
    { "dishName": "回锅肉", "count": 2 },
    { "dishName": "米饭", "count": 2 }
  ]
}

### 2.3 点不存在的菜——佛跳墙（预期 500，本课伏笔）
POST http://localhost:8080/order
Content-Type: application/json

{
  "dishList": [
    { "dishName": "佛跳墙", "count": 1 }
  ]
}
```

## 二、验证清单（全过才算下课）

程序启动后，逐个发送：

**1. 发送 2.1 查菜单**

预期响应体（6 道菜，价格是数字）：

```json
{"鱼香肉丝":16,"米饭":1,"麻婆豆腐":12,"回锅肉":18,"番茄炒蛋":10,"蛋炒饭":8}
```

> 菜的顺序可能和上面不一样——`HashMap` 本身不保证顺序，这不是 bug。想让它有序是第 8 课以后的话题。

**2. 发送 2.2 正常点单**

预期响应（自己口算一下：18×2 + 1×2 = 38，对得上说明算价逻辑对了）：

```json
{"itemList":[{"count":2,"dishName":"回锅肉","subTotal":36,"unitPrice":18},{"count":2,"dishName":"米饭","subTotal":2,"unitPrice":1}],"msg":"下单成功，请到取餐口稍等～","totalMoney":38}
```

同时看运行程序的终端，会打印：

```
[服务员] 炒好了 回锅肉 x 2
[服务员] 炒好了 米饭 x 2
```

**3. 发送 2.3 点佛跳墙（本课伏笔，必测）**

预期状态码：`500`，响应体是一段 `{"timestamp":...,"status":500,"error":"Internal Server Error",...}` 的 JSON（用浏览器访问才会看到整页 Whitelabel 错误页）。**别修它**——第 6 课的统一异常处理会回来收拾，到时你会庆幸今天见过它。

**4. 网页完整走一遍**

浏览器打开 `http://localhost:8080/`：菜单自动加载 → 给回锅肉填数量 2 → 点"下单" → 下方黑框里出现小票 JSON。

## 四、课后练习

1. **上新菜**：菜单里加"泡椒牛肉 28"，先在 `requests.http` 里加一个新点单请求验证生效。想一想：改这一行代码要重启程序——如果老板每周都调菜单怎么办？（把答案留到第 8 课验证）
2. **改小票文案**：把 `msg` 改成"已下单，请凭取餐号取餐"。
3. **思考题**：把 `@PostMapping` 改成 `@GetMapping`，重启后直接发送 2.2 那个请求会怎样？再想想为什么点单应该用 POST？（提示：GET 的语义是"要数据"，且 URL 长度有限、会被浏览器历史记录）

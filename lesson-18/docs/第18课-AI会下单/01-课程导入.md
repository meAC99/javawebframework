# 第18课 · 课程导入：AI 会下单

## 上一课发生了什么

小智上岗了，能聊天、能介绍菜品——但它是个"嘴子"：顾客说"来份不辣的下饭菜"，它回一句"好嘞"，**然后什么都没发生**。收银台没收到单，厨房没起火（字面意思），账本没进账。

今天把 AI 和业务系统**正经接起来**，两个姿势：

### 姿势一：结构化输出（AI → 订单对象）

让模型不要说人话，直接**吐 JSON**——而且是我们第 2 课就定好的那个格式：

```
顾客："来份回锅肉，两碗米饭"
模型输出：{"dishList":[{"dishName":"回锅肉","count":1},{"dishName":"米饭","count":2}]}
程序：反序列化成 OrderRequest → 直接交给第9课的 OrderService.createOrder()
```

Spring AI 的 `.entity(OrderRequest.class)` 一行搞定：框架自动把目标类的结构描述塞进提示词，模型照格式输出，框架再反序列化。**前后端第 2 课定的契约，AI 也得遵守**——这是本课最漂亮的设计呼应。

### 姿势二：工具调用（AI ← 你的数据库）

第 17 课的小智介绍菜品全靠"脑补"——菜单改价它不知道，还可能编造不存在的菜（行业黑话：**幻觉**）。工具调用（Tool Calling）反转方向：**模型自己"不会"查数据库，但它可以调用我们注册的工具方法**：

```
顾客："有什么不辣的菜？"
模型（心想）：我需要真实菜单 → 调用工具 getMenu() → 拿到 6 道菜 → 组织回答
```

工具内部就是第 8 课的 `menuRepository.findAll()`——**AI 和真人顾客走同一套代码、同一个库**。

## 先想清楚：AI 的输出可以信任吗？

不能。模型可能把"回锅肉"输出成"红烧肉"，可能给"佛跳墙"这种菜单上没有的菜。防线在哪？

**在业务校验里**——`createOrder` 里的 `findByDishName().orElseThrow(DISH_NOT_FOUND)`（第 8 课写的那行）会兜住一切胡说八道：查无此菜，40401，拒单。AI 负责"翻译人话"，**账仍由老规矩管**。这个分工认知，比任何代码都重要。

## 本课你将学会

1. `@Tool` 注解注册工具 + `defaultTools` 挂到 ChatClient
2. `.entity(Class)` 结构化输出
3. 双 ChatClient（`clone()` 出不同人设：聊天的小智 vs 点单解析器）
4. "AI 只是新入口，业务复用老收银台"的架构思维

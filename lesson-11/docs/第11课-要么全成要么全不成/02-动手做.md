# 第11课 · 动手做：装着火开关 → 出事故 → 学救人

共 5 步。**严格按顺序做**：实验一（事故）必须在加 `@Transactional` **之前**完成。

## Step 1：给墩子装"着火开关"（10 分钟）

修改 `service/SideDishService.java`——加一个从配置读的开关，打开就抛异常：

```java
package com.cdutetc.nanpo.service;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

/**
 * 墩子（配菜员）：只负责配菜这一件事——单一职责。
 * 第3课：普通 Java 类，由服务员手动 new。
 * 第4课：加上 @Service，人事权上交——由 IoC 容器创建和管理。
 * 第11课：加课堂演示开关 demo.kitchen-failure——打开后墩子配菜抛异常
 *        （模拟厨房着火），用来演示"订单已落库、后续步骤失败"时事务如何收拾残局。
 */
@Service
public class SideDishService {

    // 报到日志：证明 Bean 在容器启动时就被创建（而非第一次请求时才创建）
    public SideDishService() {
        System.out.println("[墩子] 向容器报到，单例就位：" + Integer.toHexString(System.identityHashCode(this)));
    }

    @Value("${demo.kitchen-failure:false}")
    private boolean kitchenFailure;

    public void prepareSideMaterial(String dishName, int count) {
        if (kitchenFailure) {
            // 系统级异常（不是顾客的锅）→ 走第6课 GlobalExceptionHandler 的兜底分支 {code:50001}
            throw new IllegalStateException("厨房着火了！配菜失败：" + dishName);
        }
        System.out.printf("[墩子] %s x %d 配菜完成%n", dishName, count);
    }
}
```

三个看点：

- **`@Value("${demo.kitchen-failure:false}")`**：从配置读一个布尔值，冒号后是默认值（不配置就是 false）。改开关只需动 yml，不用动代码——第 13 课的存储目录、第 16 课的 JWT 有效期，都是这个套路。
- 抛的是 `IllegalStateException`（**RuntimeException 家族**）——系统级异常，走第 6 课兜底分支变 `{code:50001}`，"不是顾客的锅"。
- 注意它**没有**用 BusinessException：着火不是业务问题，是事故。两类异常、两种处理，边界要分清。

再在 `application.yml` 末尾加配置段：

```yaml
# 第11课：课堂演示开关——厨房故障模拟。
# true 时墩子配菜抛异常，演示"订单已落库、厨房着火"时事务的作用
demo:
  kitchen-failure: false
```

## Step 2：调整下单流程——先落单，再叫厨房（10 分钟）

真实饭店的流程是：收银台先落单打小票，再喊后厨起菜。我们的代码改成一致（顺便制造出本课的教学窗口：**单已落库、厨房才着火**）。

修改 `OrderService.createOrder`——**此刻先不要加 `@Transactional`**：

```java
    // 第11课主角的位置已留好——实验一先不加它，看完事故再回来
    @Transactional   // ← 实验二才加这一行！实验一请先注释或省略
    public OrderVO createOrder(OrderRequest request) {
        // ---- 第一步：落单（验菜 → 算价 → 明细挂单 → 入库）----
        Order order = new Order();
        order.setCreateTime(LocalDateTime.now());
        BigDecimal total = BigDecimal.ZERO;

        for (OrderRequest.DishCount dc : request.getDishList()) {
            Menu menu = menuRepository.findByDishName(dc.getDishName())
                    .orElseThrow(() -> new BusinessException(ErrorCodeEnum.DISH_NOT_FOUND));

            BigDecimal subTotal = menu.getPrice().multiply(BigDecimal.valueOf(dc.getCount()));
            total = total.add(subTotal);
            order.addOrderItem(new OrderItem(dc.getDishName(), dc.getCount(), menu.getPrice(), subTotal));
        }

        order.setTotalAmount(total);
        // cascade=ALL：一次 save，主表明细全部入库
        Order saved = orderRepository.save(order);

        // ---- 第二步：叫厨房起菜 ----
        // （第11课调整：从"边点边炒"改为"先落单、后叫厨房"——真实饭店就是这么干的，
        // 同时也制造了事务教学场景：如果厨房在这里着火，刚落库的订单怎么办？）
        for (OrderItem item : saved.getOrderItems()) {
            sideDishService.prepareSideMaterial(item.getDishName(), item.getCount());
            cookService.cookDish(item.getDishName(), item.getCount());
        }

        OrderVO vo = OrderVO.from(saved);
        vo.setMsg("下单成功，请到取餐口稍等～（订单号 " + saved.getId() + "）");
        return vo;
    }
```

import 增加 `import org.springframework.transaction.annotation.Transactional;`（实验一阶段先不加注解本身）。类头注释追加一行第 11 课的店史。

对比第 10 课版本的两处变化：厨房调用从循环里**挪到了 save 之后**（不再边点边炒）；调用对象从 `dc` 换成了 `saved.getOrderItems()`（按已入库的明细起菜）。

## Step 3：实验一（事故现场）——没有事务，厨房着火（15 分钟）

1. 把 yml 里的开关改成 `kitchen-failure: true`
2. **确认 `@Transactional` 还没加上**（或注释着）
3. 重启，重放 **2.2 正常点单**，预期响应：

```json
{"code":50001,"data":null,"msg":"服务器内部错误"}
```

终端 ERROR 日志里能看到 `IllegalStateException: 厨房着火了！配菜失败：回锅肉`——第 6 课的兜底分支如约而至。

4. **关键一步，取证**：登录 h2-console 执行：

```sql
SELECT COUNT(*) FROM T_ORDER;
```

**结果：1。** 再 `SELECT * FROM T_ORDER_ITEM;`——明细也在。厨房着火了，但**脏订单留在了账本里**：钱没收齐、菜没上、厨房不知道有这单。这就是没有事务边界时"半条订单"事故的完整现场。

## Step 4：实验二（学救人）——加上 @Transactional（15 分钟）

1. 给 `createOrder` 方法加上注解和注释（正式版）：

```java
    // 第11课主角：事务边界放在业务方法上——方法内所有数据库操作同生共死，
    // 中途任何一步抛异常，已做的操作全部回滚（实验对照：不加它，厨房着火后
    // t_order 里会残留一条"钱收了、菜没炒"的脏订单）。
    // 两个经典失效坑：同类内部自调用、非 public 方法——注解悄悄不生效
    @Transactional
```

2. 开关**保持 true 不动**，重启，再次重放 2.2——响应仍是 `{code:50001}`（着火照旧）。
3. 再去 h2-console 执行 `SELECT COUNT(*) FROM T_ORDER;`

**结果：0。** 同样的事故，这次数据库**干干净净**——save 虽然执行过，但大事务回滚时连它一起撤销了。要么全成，要么全不成，这就是事务。

（如果之前实验一留了脏订单，先 `DELETE FROM T_ORDER;` 清场再数，不然数出来的 1 是旧账。）

## Step 5：关掉开关，回归正常（5 分钟）

yml 改回 `kitchen-failure: false`，重启，重放 2.2——正常下单、小票带订单号、厨房日志照常。开关留在代码里，以后随堂想演示随时打开。

> **两个"注解悄悄失效"的经典坑**（本课不展开实验，记住结论）：
> 1. **同类自调用**：在 OrderService 里 `this.createOrder(...)` 或本类方法互调——注解基于代理生效，自己调自己绕过了代理，事务不生效。
> 2. **非 public 方法**：`@Transactional` 标在 private/protected 方法上，默认不生效。
>
> 另一条规则：**默认只回滚 RuntimeException**——`IllegalStateException` 是它的子类，所以实验二能回滚。受检异常（Checked Exception）默认不回滚，需要 `@Transactional(rollbackFor = Exception.class)` 显式声明。

# 第5课 · 课程导入：全店统一小票

## 上一课发生了什么

员工归容器管了，架构清爽了。但站在**看你接口的人**（前端、未来的你、AI）角度，这家店说话还很难懂：

| 接口 | 返回 | 前端拿到后 |
|---|---|---|
| `GET /hello` | 一段文字 | 直接显示 |
| `GET /menu` | 裸 Map `{"回锅肉":18}` | 遍历渲染 |
| `POST /order` | 小票对象 | 取字段渲染 |

三种格式、三种解析逻辑，而且**没法统一表达"失败"**——成功时没有"成功码"，失败时（点错菜）直接是一屏 500。前端同学每加一个接口就要重新猜一次你的心思。

## 今天要定的店规：统一返回

所有接口的返回都装进同一种"信封"：

```json
{
  "code": 200,          ← 数字状态码：200 成功；4 开头业务失败；5 开头系统错误
  "msg": "操作成功",     ← 给人看的信息
  "data": { ... }       ← 给程序用的数据（真正的载荷）
}
```

要做两件事：

1. 写一个泛型类 `Result<T>`——`T` 是 data 的类型，同一张信封能装菜单、装订单、装任何东西（**泛型**是本课的 Java 语言知识点）
2. 把现有三个接口全部套上信封，**同时**改前端页面适配新格式——这节课你会亲身体会：**后端改了契约，前端不改就白屏**。这不是坑，是全栈的基本意识。

## 本课你将学会

1. 泛型类设计：`Result<T>` 为什么能装一切
2. 静态工厂方法：`Result.success(x)` / `Result.fail(...)` 为什么比 new + set 三连舒服
3. 错误码字典：用枚举统一管理 code 和 msg
4. 接口契约变更时的前后端同步改造

## 先想一个问题：data 为什么必须是泛型？

菜单是 `Map<String, Integer>`，订单是 `OrderResponse`，开业标语是 `String`——如果信封的 data 字段写成固定类型，每类数据就得各造一个信封类。写成 `Result<T>`，data 的类型由使用者指定：`Result<Map<String, Integer>>`、`Result<OrderResponse>`……**一张信封，装一切**。这就是泛型的价值：把"变化的类型"参数化。

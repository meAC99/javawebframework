# 第5课 · 验证、提交与练习

## 一、验证清单（全过才算下课）

程序运行中，逐个发送 `requests.http` 里的请求（本课不新增请求——**同一批请求，预期输出变了**，这正是契约变更的直观体现）。

**1. 发送 1.1 开业检查**

预期（第 1 课它返回裸文字，现在套上了信封）：

```json
{"code":200,"data":"南坡小炒，本店开业！","msg":"操作成功"}
```

**2. 发送 2.1 查菜单**

预期（菜单现在住在信封的 `data` 里）：

```json
{"code":200,"data":{"鱼香肉丝":16,"米饭":1,"麻婆豆腐":12,"回锅肉":18,"番茄炒蛋":10,"蛋炒饭":8},"msg":"操作成功"}
```

**3. 发送 2.2 正常点单**

预期：信封套着小票，`data.totalMoney` 为 38：

```json
{"code":200,"data":{"itemList":[{"count":2,"dishName":"回锅肉","subTotal":36,"unitPrice":18},{"count":2,"dishName":"米饭","subTotal":2,"unitPrice":1}],"msg":"下单成功，请到取餐口稍等～","totalMoney":38},"msg":"操作成功"}
```

注意这里有两个 msg：外层是信封的"操作成功"，内层是小票的"下单成功"——一个给前端框架看，一个给顾客看。

**4. 发送 2.3 点佛跳墙（伏笔仍在）**

预期：仍是状态码 `500`——本课只统一了**正常返回**，异常还是老样子，第 6 课处理。前端页面上点错菜会显示 `❌ 服务器开小差了（500）`（就是 Step 4 里那个 `.catch` 分支接住的）。

**5. 浏览器完整回归**：点餐页菜单正常渲染、下单后黑框里展示完整信封 JSON（code/msg/data 一眼可见）。

## 三、课后练习

1. **给字典加词**：在 `ErrorCodeEnum` 里加一个 `SHOP_CLOSED(40001, "打烊了，明天请早")`，再写个临时接口返回 `Result.fail(ErrorCodeEnum.SHOP_CLOSED)`，往 `requests.http` 加个请求看看信封长什么样。做完删掉临时代码和请求。
2. **动手实验**：把 `Result.success(...)` 静态工厂里的三行 set 换成构造器 + `@AllArgsConstructor` 试试——说说静态工厂比"new + 全参构造"好在哪？（提示：命名、返回值类型可以是父类/接口、可以控制实例）
3. **思考题**：前端现在每个请求都要写 `result.data` 和判断 `result.code`。试着自己封装一个统一的 `request()` 函数（拆信封、判断 code、失败统一提示），替换页面里的两处 fetch——写完你会发现，前端也需要一个"统一返回"。

## 四、下一课预告

现在成功时回信封、失败时喷 500——顾客点错一道菜，看到的还是一段机器味的报错。下一课，你给店里建一个统一的"客诉处理台"（`@RestControllerAdvice`）：**任何接口抛出的任何异常，都由它转成规范的信封**。业务上的小问题（点错菜）和系统级事故（程序炸了）分开处理、分开记日志——连第 1 课那个 `404 + timestamp` 的报错，也会被优雅地接住。

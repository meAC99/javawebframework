# 第4课 · 验证、提交与练习

## 一、验证清单（全过才算下课）

**1. 启动日志：无请求，先报到**

程序启动后（**什么都别点**），终端应出现：

```
[墩子] 向容器报到，单例就位：xxxxxxx
[厨师] 向容器报到，单例就位：xxxxxxx
...（若干 Spring 日志）
Started NanpoApplication in x.xxx seconds
```

两个结论自己敲定：

- 报到在 `Started` **之前** → Bean 是**容器启动时**创建的，不是第一次请求时才创建。开门营业前员工全部到岗。
- 每人只报到**一次** → 全店一份（单例）。之后无论多少请求、多少个使用者，用的都是这一个对象。

**2. 下单：一切照旧**

打开 `requests.http`，重新发送 **2.2 正常点单**。

预期：`totalMoney: 38`；日志打出 `[墩子] 回锅肉 x 2 配菜完成` → `[厨师] 回锅肉 x 2 炒菜完成`（和第 3 课一致），且**不再重复报到**（单例不重建）。

**3. 浏览器回归**：点餐页正常下单一次。

三步全过，你完成了这门课到目前为止最"安静"的一次重构：对外行为零变化，内部权力结构天翻地覆。

## 三、课后练习

1. **眼见为实——单例验证**：在 `WaiterController` 里临时加一个接口，返回 `Integer.toHexString(System.identityHashCode(sideDishService))`；再给某个 Service 加一个同样的接口（返回自己的哈希码）。多次访问两个接口——墩子的哈希码和你字段里注入的是否始终相同？（做完把临时代码删掉，别提交）
2. **三个注解换个位置试试**：把 `@Service` 改成 `@Component`，重启——能用吗？结论写进你的笔记：它们的区别在机制还是语义？
3. **思考题**：如果容器里有**两个**厨师类型的 Bean（比如大厨和二厨），`@Autowired CookService cookService` 会注入哪一个？会报错吗？（答案关键词：`@Primary`——设一个默认优先；`@Qualifier`——点名要哪一个。带着猜想去查证，把结论写进笔记）

## 四、下一课预告

人事理顺了，店也分工明确了。但你打开浏览器看看三个接口的返回：`/hello` 返回字符串、`/menu` 返回裸 Map、`/order` 返回小票对象——**三个接口三种格式**。前端同学每接一个接口就要写一套解析逻辑，出错时更没处下手。

下一课，你给全店定一条店规：**所有接口统一用一种"小票"回话**——`Result{code, msg, data}`。后端改格式，前端必须同步改——你将第一次完整经历"接口契约变更"的前后端联动。

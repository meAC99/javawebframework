# 第14课 · 验证、提交与练习

## 一、requests.http 追加

```
### 14.1 照片直出（把上一课上传返回的 uuid.png 填进来；预期 200 image/png）
GET http://localhost:8080/files/<uuid.png>

### 14.2 下载照片（预期 200，响应头 Content-Disposition: attachment）
GET http://localhost:8080/download/<uuid.png>

### 14.3 下载不存在的文件（预期 code=40405）
GET http://localhost:8080/download/nope.png

### 14.4 路径穿越攻击演练（预期：被拦，Tomcat 返回 400）
GET http://localhost:8080/download/..%2Fpom.xml
```

## 二、验证清单（全过才算下课）

**0. 先传照片**：重启后 H2 内存库清空了 imageUrl——重发 13.1 给回锅肉上架照片，记下新 uuid。

**1. 发送 14.1**：状态 200、`Content-Type: image/png`（响应头里看），第 13 课的钩子正式结案。

**2. 发送 14.2**：状态 200，展开响应头找到——

```
Content-Disposition: attachment; filename="<uuid>.png"
```

`attachment` 就是"另存为"的指令。把 URL 贴到浏览器地址栏试一次：这次浏览器**不显示**图片，直接下载。同一张图，14.1 直接看、14.2 下载——一个响应头的差别。

**3. 发送 14.3** → `{"code":40405,"data":null,"msg":"文件不存在"}`——下载接口的业务异常照旧走处理台。

**4. 发送 14.4 路径穿越**：预期得到 **HTTP 400 Bad Request**（Tomcat 的 HTML 错误页，不是我们的信封）。**两层防线各司其职**：编码过的 `../`（`%2F`）在 Tomcat 的 URL 层就被拒了（400）；就算漏进来，Controller 里的 `startsWith(root)` 也会把它按 40405 拒掉——纵深防御。安全上"多一道关卡"永远不亏。

**5. 上传超限**：造一个 3MB 大文件（IDEA 里随便复制粘贴出一个大文本改名 `big.png`，或找张高清图），仿照 13.1 发送 → `{"code":40406,"data":null,"msg":"上传文件超过大小限制（最大 2MB）"}`，终端有 warn 日志。注意观察：**Controller 的 uploadImage 完全没执行**（断点/日志可证）——超限死在解析阶段，处理台接的正是这一口。

**6. 菜单带图（本课的颜值验收）**：重发 2.1 → 数组结构，回锅肉带 `imageUrl`；浏览器强刷点餐页——**回锅肉有照片，其他菜 🍽️ 占位**。没传图的菜不会裂图，占位图标兜底。

**7. 回归**：2.2 下单、12.1 分页、6.1 佛跳墙——全部如常。

## 三、课后练习

1. **inline 实验**：把下载接口的 `attachment` 改成 `inline`，重启重发 14.2——浏览器行为变了吗？（变成直接打开。两个词的差异，值得亲手摸一次。做完改回 attachment。）
2. **收紧限额**：把 `max-file-size` 改成 `200KB`，重启，传你那张 dish.png——如果它超过 200KB 就会被拒（40406 的 msg 还是"最大 2MB"，发现文案和配置不同步的问题了吗？想想错误码字典的 msg 该怎么跟配置联动——比如用 `Result.fail(code, "上传文件超过大小限制（最大 " + 限额 + "）")` 动态拼。改回 2MB 收尾。）
3. **思考题**：既然 `/files/**` 已经能访问图片，为什么还要单独的 `/download` 接口？（提示：不是所有文件都该"直接看"——报表 Excel、打包 zip 必须走下载；另外下载接口能加权限，静态映射默认人人可访问——这个差别第 16 课之后你会更有感触。）

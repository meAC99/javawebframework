# 第16课 · 验证、提交与练习

## 一、requests.http 追加

先重发 15.1 注册（H2 重启清零）、15.3 登录。登录响应里现在有**两张卡**，把它们分别复制出来，粘到下面各请求的 `<accessToken>` / `<refreshToken>` 占位处：

```
### 16.1 不带令牌下单（预期 code=40101 请先登录）
POST http://localhost:8080/order
Content-Type: application/json

{ "dishList": [ { "dishName": "米饭", "count": 1 } ] }

### 16.2 伪造令牌下单（预期 code=40102）
POST http://localhost:8080/order
Content-Type: application/json
Authorization: Bearer fake.token.here

{ "dishList": [ { "dishName": "米饭", "count": 1 } ] }

### 16.3 短卡(accessToken)下单（预期 200，订单记名）
POST http://localhost:8080/order
Content-Type: application/json
Authorization: Bearer <accessToken>

{ "dishList": [ { "dishName": "回锅肉", "count": 1 } ] }

### 16.4 长卡(refreshToken)当短卡用（预期 40102——各卡各用）
POST http://localhost:8080/order
Content-Type: application/json
Authorization: Bearer <refreshToken>

{ "dishList": [ { "dishName": "米饭", "count": 1 } ] }

### 16.5 续卡：长卡换新短卡（预期返回新的 accessToken/refreshToken）
POST http://localhost:8080/refresh
Content-Type: application/json

{ "refreshToken": "<refreshToken>" }

### 16.6 拿短卡来续卡（预期 40102）
POST http://localhost:8080/refresh
Content-Type: application/json

{ "refreshToken": "<accessToken>" }

### 16.7 翻账本看订单记名（预期 records 里有 username）
GET http://localhost:8080/order/list?page=0&size=5
Authorization: Bearer <accessToken>
```

（注意 16.1/16.2 故意不带/带假令牌；12.1 那个老的翻账本请求从本课起也要加 `Authorization` 头了，否则 40101。）

## 二、验证清单（六场景全过才算下课）

**0. 解码对比两张卡**：把 15.3 返回的 accessToken 和 refreshToken 分别粘到 jwt.io——预期：

- accessToken：`"type": "access"`，`exp - iat = 900` 秒（15 分钟）
- refreshToken：`"type": "refresh"`，`exp - iat = 604800` 秒（7 天 = 10080 分钟）

同一个用户、同一个签名密钥，只差 type 和有效期——设计就是如此简洁。

**场景 1 ｜ 发送 16.1（无票）** → `{"code":40101,...,"msg":"请先登录（缺少令牌）"}`

**场景 2 ｜ 发送 16.2（假票）** → `{"code":40102,...,"msg":"令牌无效或已过期，请重新登录"}`

**场景 3 ｜ 发送 16.3（短卡下单）** → 正常小票（订单号、总额），并且——

**场景 4 ｜ 订单记名**：发送 16.7 → `records` 里每笔订单带 `"username":"xiaoming"`；h2-console `SELECT ID, USER_ID, USERNAME, TOTAL_AMOUNT FROM T_ORDER;` 同样可见。**下单的人，账本记住了。**

**场景 5 ｜ 发送 16.4（长卡当短卡）** → 40102。长卡是真票也不行——**卡种不符**，拦截器的 type 校验在把关。

**场景 6 ｜ 续卡二连**：发送 16.5 → 返回全新的一对卡（把新 accessToken 粘回 16.3 再发，照常 200）；发送 16.6（短卡来续）→ 40102。

**浏览器端**：点餐页顶部有登录框——不登录直接点"下单"，结果区显示 `❌ 请先登录（缺少令牌）（code=40101）`；登录后再下单，一气呵成。刷新页面仍保持登录（localStorage 的功劳）。

**回归**：2.1 查菜单、13.1 传照片、14.1 看照片——全部不需要令牌（本店规矩：逛店自由）。

## 四、课后练习

1. **等一张卡过期（体感 15 分钟）**：登录后把 accessToken 放着，15 分钟后重发 16.3 → 40102（`ExpiredJwtException`）；再用长卡走 16.5 续出新高照常下单。整个"短卡过期→长卡续命"的无感续期闭环，值得亲手走一遍。（等不了 15 分钟？把 `access-ttl-minutes` 临时改成 1，吃完一顿饭的功夫就够。）
2. **串号事故复现（理解 clear 的意义）**：把 `JwtInterceptor.afterCompletion` 里的 `UserContext.clear()` 注释掉，重启；登录下单一次（正常），然后**不登录**直接发 16.1——理论上应 40101，但你会发现……多试几次，观察是否偶发"捡到上一个请求的登录人"下单成功。线程池串号是概率性的，**偶发 bug 比必现 bug 可怕十倍**——这就是那行 clear 的分量。（复现后必须还原！）
3. **思考题**：现在前端收到 40102 时只会显示错误，让用户手动重新登录。能不能自动处理？（提示：收到 40102 → 拿 localStorage 里的长卡调 /refresh → 成功就用新卡重发原请求、失败才提示登录。这套"自动续期拦截"就是 axios 拦截器/fetch 封装的经典应用——第 5 课思考题的Pro版。）

## 拓展一眼：工业级的它们

- **Spring Security**：你这两课手写的整套体系（BCrypt、过滤/拦截、Bearer 解析、权限规则），生产世界的工业化版本叫 Spring Security——过滤器链 + 方法级注解的一整套全家桶，第 15 课我们只借了它一个工具类。手写一遍的意义正在于：将来用 Security 时，你知道它内部每一步在干什么。
- **OAuth2 / 单点登录**：双卡设计再往外走一步——"用微信登录南坡小炒"就是 OAuth2 的场景，refreshToken 的思想在其中的 refresh token/grant 里如出一辙。课程不展开，留给你按图索骥。

# 第10课 · 动手做：先引爆，再分离

共 6 步。Step 1 是"事故现场"，代码看完即删；Step 2-6 是正式改造。

## Step 1：开场实验——实体直出，当场爆炸（15 分钟）

在 `WaiterController.java` 里**临时**加一个端点（看着别扭的写法也是故意的——爆炸之后全部删除）：

```java
    // =====【课堂实验专用：观察完立即删除】=====
    // 反面教材：把 Order 实体直接序列化给前端会怎样？
    // Order → orderItems → 每个 item 的 order → 又回到 Order …… 无限递归
    @Autowired
    private com.cdutetc.nanpo.dao.OrderRepository demoOrderRepository;

    @GetMapping("/order/{id}/raw")
    public Result<com.cdutetc.nanpo.entity.Order> raw(@org.springframework.web.bind.annotation.PathVariable Long id) {
        return Result.success(demoOrderRepository.findById(id).orElseThrow());
    }
```

重启，先重放 2.2 下一单（保证库里有一张订单），然后往 `requests.http` 里临时加：

```
### 【实验】实体直出（预期：出事故）
GET http://localhost:8080/order/1/raw
```

发送。你会看到：响应体**空空如也**（或一截截断的 JSON）。真正的事故证据在服务端终端，从上往下找 ERROR 附近：

```
HttpMessageNotWritableException: Could not write JSON:
Document nesting depth (501) exceeds the maximum allowed (500, ...)
```

读出三层信息：

1. **递归真的发生了**：Jackson 沿着 Order↔OrderItem 的双向引用一层层套下去；
2. **501 层被拦下了**：新版 Jackson 有嵌套深度保护（500 层上限）——老版本没有这层保险，直接就是 `StackOverflowError`；
3. 响应头已经发出（HTTP 200），正文写了一半——所以前端拿到的是残缺响应，**比 500 更难排查**。

**实验完毕，删除临时代码**（端点、注入、requests.http 里的请求，全删），恢复原样。

## Step 2：新住户入户——dto 与 vo（15 分钟）

**① `dto/OrderRequest.java`**——入参乔迁（从 pojo 包搬来，包名和注释更新，内容不变）：

```java
package com.cdutetc.nanpo.dto;

import java.util.List;

import lombok.Data;

/**
 * 点单请求 DTO（入参：前端 → 后端）。
 * 第10课：从 pojo 包迁入 dto 包并正名——DTO 专职"传输"，不含业务逻辑。
 * 对应 JSON：{"dishList":[{"dishName":"回锅肉","count":2}]}
 */
@Data
public class OrderRequest {

    private List<DishCount> dishList;

    @Data
    public static class DishCount {
        private String dishName;
        private Integer count;
    }
}
```

**② `vo/OrderItemVO.java`**——小票明细行（出参）：

```java
package com.cdutetc.nanpo.vo;

import java.math.BigDecimal;

import com.cdutetc.nanpo.entity.OrderItem;

import lombok.Data;

/**
 * 小票明细行 VO（出参：后端 → 前端）。
 * 第10课新增：字段按前端需要从订单明细实体裁剪而来——
 * 实体上的 id、order 外键等账本细节，前端不需要就不给看。
 */
@Data
public class OrderItemVO {

    private String dishName;
    private Integer count;
    private BigDecimal unitPrice;
    private BigDecimal subTotal;

    // 静态工厂转换：实体 → VO 集中一处，改字段只动这一个文件
    public static OrderItemVO from(OrderItem item) {
        OrderItemVO vo = new OrderItemVO();
        vo.setDishName(item.getDishName());
        vo.setCount(item.getCount());
        vo.setUnitPrice(item.getUnitPrice());
        vo.setSubTotal(item.getSubTotal());
        return vo;
    }
}
```

**③ `vo/OrderVO.java`**——小票整体（出参）：

```java
package com.cdutetc.nanpo.vo;

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

import com.cdutetc.nanpo.entity.Order;
import com.cdutetc.nanpo.entity.OrderItem;

import lombok.Data;

/**
 * 订单小票 VO（出参：后端 → 前端）。
 * 第10课新增：账本（entity.Order）不能直接发给前端——
 * 双向关联会被 JSON 无限递归、懒加载随时炸、实体字段（如以后的密码）全部裸奔；
 * VO 按前端需要裁剪字段，实体永不出 Service 之外。
 */
@Data
public class OrderVO {

    private Long orderId;
    private List<OrderItemVO> itemList;
    private BigDecimal totalMoney;
    private String msg;

    // 静态工厂转换：账本 → 小票。第9课里 pojo 与实体同名的别扭（全限定名）
    // 在这一步彻底消失——pojo 退役，vo 与 entity 各归各位、井水不犯河水
    public static OrderVO from(Order order) {
        OrderVO vo = new OrderVO();
        vo.setOrderId(order.getId());
        vo.setTotalMoney(order.getTotalAmount());
        List<OrderItemVO> items = new ArrayList<>();
        for (OrderItem item : order.getOrderItems()) {
            items.add(OrderItemVO.from(item));
        }
        vo.setItemList(items);
        return vo;
    }
}
```

品味 `from()`：转换逻辑集中在**一处**——哪天小票要加字段（比如下单时间），只改 `OrderVO.from()` 一个方法，所有出口同时生效。这就是"集中转换"对"循环里抄两遍"的胜利。

## Step 3：OrderService 改造——上一课的别扭当场消失（15 分钟）

`createOrder` 的返回类型换成 `OrderVO`，方法体大瘦身：

```java
    public OrderVO createOrder(OrderRequest request) {
        Order order = new Order();
        order.setCreateTime(LocalDateTime.now());
        BigDecimal total = BigDecimal.ZERO;

        for (OrderRequest.DishCount dc : request.getDishList()) {
            String dishName = dc.getDishName();
            Integer count = dc.getCount();

            // 验菜+取价（查库）
            Menu menu = menuRepository.findByDishName(dishName)
                    .orElseThrow(() -> new BusinessException(ErrorCodeEnum.DISH_NOT_FOUND));

            BigDecimal subTotal = menu.getPrice().multiply(BigDecimal.valueOf(count));
            total = total.add(subTotal);

            // 账本侧：明细实体挂上订单（unitPrice 价格快照）。
            // 第10课收益：pojo 退役后，entity.OrderItem 可以正常 import——
            // 第9课里那行全限定名的别扭不复存在
            order.addOrderItem(new OrderItem(dishName, count, menu.getPrice(), subTotal));

            // 厨房编排
            sideDishService.prepareSideMaterial(dishName, count);
            cookService.cookDish(dishName, count);
        }

        order.setTotalAmount(total);
        // cascade=ALL：一次 save，主表明细全部入库
        Order saved = orderRepository.save(order);

        // 小票侧：账本 → 小票一把转换（OrderVO.from 内部完成明细级转换）
        OrderVO vo = OrderVO.from(saved);
        vo.setMsg("下单成功，请到取餐口稍等～（订单号 " + saved.getId() + "）");
        return vo;
    }
```

对照第 9 课的三个变化：import 里 `entity.OrderItem` 正常登场（全限定名没了）；"小票侧并行拼"的 7 行没了（被 `OrderVO.from(saved)` 一行取代）；import 的 `pojo.*` 全换成 `dto.OrderRequest` 和 `vo.OrderVO`。类头注释同步更新。

## Step 4：Controller 改签名（5 分钟）

`WaiterController` 的 `/order`：

```java
    @PostMapping("/order")
    public Result<OrderVO> order(@RequestBody OrderRequest orderRequest) {
        return Result.success(orderService.createOrder(orderRequest));
    }
```

import 换成 `com.cdutetc.nanpo.dto.OrderRequest` 和 `com.cdutetc.nanpo.vo.OrderVO`。从今天起，**Controller 的世界里再无实体**——进是 dto，出是 vo。

## Step 5：pojo 包退役（5 分钟）

删掉整个 `pojo` 包（`OrderRequest` / `OrderItem` / `OrderResponse` 三个文件都已各奔新家或被 VO 取代）。

第 2 课它以"装数据的口袋"身份出生，当时请求和响应不分你我；现在 dto/vo 各司其职，它的历史使命完成了。**删除也是一种致敬。**

## Step 6：重启 + 检查包结构（5 分钟）

重启前先自查目录，应该是清爽的"一主八包"：

```
com.cdutetc.nanpo
├── NanpoApplication   主启动类
├── common             Result/错误码/异常/客诉处理台
├── config             MenuDataInitializer 等配置类
├── controller         WaiterController / HelloController
├── dao                MenuRepository / OrderRepository
├── dto                OrderRequest
├── entity             Menu / Order / OrderItem
├── service            OrderService / 墩子 / 厨师
└── vo                 OrderVO / OrderItemVO
```

> **常见报错**
>
> | 现象 | 原因 | 解法 |
> |---|---|---|
> | 到处飘红 `OrderResponse 找不到` | pojo 删了但 Controller/Service 还引用旧类 | 按 Step 3/4 换成 vo |
> | `无法将 OrderItem 转换为 OrderItemVO` | from() 忘了在循环里调用 | 对照 Step 2 的 from 写法 |

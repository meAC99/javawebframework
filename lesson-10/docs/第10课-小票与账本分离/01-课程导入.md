# 第10课 · 课程导入：小票与账本分离（DTO/VO）

## 上一课发生了什么

订单落库了，但留下了两个你亲手写过的坏味道：实体 `OrderItem` 和小票据 `OrderItem` 同名打架，只能用全限定名区分；下单循环里"账本侧"和"小票侧"两套对象并行拼，同一份数据抄了两遍。

今天开场先引爆一颗一直没响的雷。

## 开场实验预告：实体直接出库，会当场爆炸

现在的 `OrderVO`……不对，现在还只有 `OrderResponse`（小票）。假如某个新同事图省事，把 `/order` 的返回值直接改成实体 `Result<Order>`——"实体里数据最全，直接给它不就完了？"

想一下会发生什么：Jackson 开始序列化 Order → 打开 orderItems 列表 → 序列化每个 OrderItem → 它有个 `order` 字段又指回订单 → 再序列化订单 → 又打开 orderItems → ……**你抓着这个环转一辈子也转不完**。

这不是理论风险，是新手真实会犯的错。下一文件第一步，你就加一段临时代码亲手引爆它（放心，引爆完立刻删），然后带着"为什么"进入本课的正题。

## 本课主角：dto / vo / entity 三层对象各司其职

爆完之后，用一套行业通行的对象分层把问题连根拔掉：

| 层 | 包 | 职责 | 谁能碰数据库 |
|---|---|---|---|
| **entity（实体/账本）** | `entity` | 数据库表的影子，怎么存数据方便怎么来 | 只有它能 |
| **dto（数据传输对象/单据）** | `dto` | 入参：前端 → 后端 的请求载体 | 不能 |
| **vo（视图对象/小票）** | `vo` | 出参：后端 → 前端 的响应载体，按前端需要裁剪 | 不能 |

从此数据像物流一样流动：**请求(dto) → 业务处理(entity) → 响应(vo)**，每一段边界清晰。第 2 课出生的 `pojo` 包（当时职责模糊，请求响应混住）整体退役，三个类各奔新家。

## 本课你将学会

3. 用一次"包重组"同时消灭上一课的两个坏味道

## 先想清楚：字段泄露为什么也危险？

循环引用和懒加载是"当场爆炸"，第三宗罪是"慢性中毒"：实体字段**全量**暴露。现在 Order 的字段无害，但想一件事——第 15 课会有 `User` 实体，上面有 `password` 字段（哪怕是加密后的哈希）。如果那时有人习惯性把 User 实体直接序列化返回……密码哈希就裸奔在每一个响应里。**对象分层不是洁癖，是安全边界。**

# 第6课 · 动手做：BusinessException + 大堂经理 + 前端分流

共 5 步：错误码加词 → 业务异常 → 处理台 → 服务员手术 → 前端分流。

## Step 1：错误码字典加词（3 分钟）

打开 `common/ErrorCodeEnum.java`，在 `DISH_NOT_FOUND` 下面加一行：

```java
    /* 4xxxx 业务类错误 */
    DISH_NOT_FOUND(40401, "该菜品不存在"),
    PATH_NOT_FOUND(40404, "访问路径不存在"),   // ← 新增
```

`PATH_NOT_FOUND` 给谁用？马上就知道——它是给"访问了不存在的路径"（404 类错误）准备的。这个坑很隐蔽：404 看起来不像异常，但如果不管它，它会被最后面的"系统异常兜底"误接，把"走错门"报成"店里炸了"。

## Step 2：业务异常 BusinessException（10 分钟）

新建 `common/BusinessException.java`：

```java
package com.cdutetc.nanpo.common;

import lombok.Getter;

/**
 * 业务异常：顾客的问题（点的菜不存在、库存不够…），对应 4xxxx 错误码。
 * 第6课引入：和"系统异常"区分开——
 * 业务异常是正常经营中的预期情况，记 warn 级别即可；
 * 系统异常才是真事故，要记 error 并排查。
 */
public class BusinessException extends RuntimeException {

    @Getter
    private final Integer code;

    public BusinessException(ErrorCodeEnum errorCodeEnum) {
        super(errorCodeEnum.getMsg());
        this.code = errorCodeEnum.getCode();
    }
}
```

看懂三个设计点：

- **继承 RuntimeException**：调用方不用强制 try-catch，想抛就抛（原因见课程导入）。
- **携带错误码**：抛异常时塞进一个 `ErrorCodeEnum`，msg 和 code 都从字典来——错误信息永远有出处，不会手抖打错字。
- **字段上的 `@Getter`**：lombok 也支持给单个字段生成 getter，`getCode()` 供处理台取码用。

## Step 3：大堂经理 GlobalExceptionHandler（20 分钟）

新建 `common/GlobalExceptionHandler.java`——本课主角：

```java
package com.cdutetc.nanpo.common;

import lombok.extern.slf4j.Slf4j;

import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.servlet.resource.NoResourceFoundException;

/**
 * 全店统一的"客诉处理台"：第6课。
 * 无论哪个接口抛出异常，都在这里转成规范的 Result 小票，不再向前端喷异常栈。
 * 三级分流：业务异常(warn) → 路径不存在(404类) → 系统异常(error 兜底)
 */
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 业务异常：预期之内的小问题（如点了不存在的菜），warn 记录即可
    @ExceptionHandler(BusinessException.class)
    public Result<?> handleBusiness(BusinessException e) {
        log.warn("业务异常 code={}, msg={}", e.getCode(), e.getMessage());
        return Result.fail(e.getCode(), e.getMessage());
    }

    // 访问了不存在的路径/静态资源：真实坑——不单独处理的话，
    // 它会掉进下面的 Exception 兜底，被误报成"服务器内部错误"
    @ExceptionHandler(NoResourceFoundException.class)
    public Result<?> handleNoResource(NoResourceFoundException e) {
        log.warn("路径不存在: {}", e.getMessage());
        return Result.fail(ErrorCodeEnum.PATH_NOT_FOUND);
    }

    // 系统异常兜底：真事故——error 级别记录完整堆栈，对顾客只说"内部错误"
    @ExceptionHandler(Exception.class)
    public Result<?> handleAll(Exception e) {
        log.error("系统异常: ", e);
        return Result.fail(ErrorCodeEnum.SYSTEM_ERROR);
    }
}
```

逐个看懂：

- **`@RestControllerAdvice`**：全店生效的"环绕通知"。它相当于对**所有** Controller 说：你们抛出的异常先送到我这。加上 `@RestController` 的含义（返回值直接进响应体），它处理完返回的 `Result` 会自动转成 JSON。
- **`@ExceptionHandler(Xxx.class)`**：本方法负责接哪类异常。三个方法从上到下就是**三级分流**——先认领业务异常，再认领 404 类，剩下的全归兜底。Spring 会按"最精确的类型匹配"来路由，不会抢。
- **`@Slf4j`**：lombok 一行生成日志对象 `log`，从此告别 `System.out.println`。注意两个日志的差别：
  - `log.warn(...)`：业务异常只记一行摘要——它每天都在发生（有人就是会点错菜），不值得刷屏；
  - `log.error("系统异常: ", e)`：把异常对象 `e` 传进去，**完整堆栈**进日志——真事故必须留全证据。
- **对顾客只说该说的**：系统异常的处理里，日志记了完整堆栈，但返回给前端的只是 `SYSTEM_ERROR(50001, "服务器内部错误")`——堆栈里有表结构、类名路径，泄露给外界就是安全事件。

## Step 4：服务员手术——换一种抛法（10 分钟）

修改 `WaiterController.java` 点单方法里的校验段，**删掉**旧的裸抛：

```java
            // 删除：第2课的裸抛
            // throw new RuntimeException("菜品不存在：" + dishName);
```

换成：

```java
            // 菜单里没有这道菜：第6课整改——从第2课的裸 RuntimeException
            // 升级为带错误码的业务异常，交给 GlobalExceptionHandler 统一处理
            if (!MENU.containsKey(dishName)) {
                throw new BusinessException(ErrorCodeEnum.DISH_NOT_FOUND);
            }
```

顶部补 import：

```java
import com.cdutetc.nanpo.common.BusinessException;
import com.cdutetc.nanpo.common.ErrorCodeEnum;
```

类头注释追加一行店史：

```java
 * 第6课：客诉统一——业务问题抛 BusinessException，由 GlobalExceptionHandler 全局兜住。
```

体会变化：抛异常还是那一行，但抛的**东西**不同了——以前是一句裸字符串，现在是一个带错误码、有身份的异常对象，处理台能认出它、按规矩分流。

## Step 5：前端分流——把信封里的错误显示出来（10 分钟）

现在点错菜后端会回 `{code:40401, msg:"该菜品不存在"}`（状态码 200，信息在信封里），但前端第 5 课写的逻辑是"把整个信封打印出来"。给它升级：按 `code` 分流。

修改 `index.html` 中 `order()` 里的 `.then(...)` 部分：

```js
        .then(resp => resp.json())
        .then(result => {
            // 第6课适配：后端统一异常处理后，业务错误也能拿到规范 JSON 了
            // （第5课时点错菜还是 500 HTML 丑页，现在按 code 分流展示）
            if (result.code === 200) {
                document.getElementById('result').innerText = JSON.stringify(result, null, 2);
            } else {
                document.getElementById('result').innerText = '❌ ' + result.msg + '（code=' + result.code + '）';
            }
        })
```

`result.code === 200` 走成功展示，否则把 `msg` 用红字提示出来——**前后端终于说同一种"错误语言"了**。外层那个 `.catch()` 保留（网络断开等极端情况的兜底），但从这节课起基本走不到了。

改完重启程序（改了 Java 代码必须重启）。

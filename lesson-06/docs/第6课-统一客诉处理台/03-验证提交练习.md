## 一、requests.http 追加两个请求

```
### 6.1 点不存在的菜（预期：状态码200，信封里 code=40401——不再是500丑页）
POST http://localhost:8080/order
Content-Type: application/json

{
  "dishList": [
    { "dishName": "佛跳墙", "count": 1 }
  ]
}

### 6.2 访问不存在的路径（预期：信封里 code=40404）
GET http://localhost:8080/no-such-page
```

## 二、验证清单（全过才算下课）

**1. 发送 6.1 点佛跳墙——第 2 课的伏笔兑现**

预期响应（对照第 5 课验证时的 500 + timestamp，天壤之别）：

```json
{"code":40401,"data":null,"msg":"该菜品不存在"}
```

注意：**HTTP 状态码是 200，错误信息在信封的 code 里**——这是本课程的约定（国内教学惯例：用业务码区分成败，HTTP 层面统一 200）。真实项目里也有人用 HTTP 401/404/500 表达，两种流派课后练习里让你思考。

同时看程序终端的日志，预期一行**简短**的 warn：

```
WARN ... 业务异常 code=40401, msg=该菜品不存在
```

没有堆栈——因为这不是事故，是有人点错了菜。

**2. 发送 6.2 访问不存在的路径**

预期：

```json
{"code":40404,"data":null,"msg":"访问路径不存在"}
```

**3. 重放 1.2（第 1 课的伏笔也兑现了）**

重新发送第 1 课写的 `GET /nobody-home`——第 1 课它返回 `{"timestamp":...,"status":404,...}`，现在返回的是和上面一样的 40404 信封。**一个处理台，接住了全店所有出口。**

**4. 回归：正常流程无损**

- 重发 **2.2 正常点单** → `code:200`，`totalMoney:38`
- 重发 **2.1 查菜单** → 正常
- 浏览器打开 `http://localhost:8080/`，点一份"佛跳墙"（先在菜单数量框随便填，手动改？不行——页面上没有佛跳墙。你可以临时用开发者工具 Console 执行一句 `fetch('/order',{method:'POST',headers:{'Content-Type':'application/json'},body:JSON.stringify({dishList:[{dishName:'佛跳墙',count:1}]})}).then(r=>r.text()).then(console.log)` 模拟点错菜），页面上会显示 `❌ 该菜品不存在（code=40401）`——错误消息终于说人话了。

## 四、课后练习

1. **分流实验**：把 `GlobalExceptionHandler` 里 `@ExceptionHandler(Exception.class)` 那个方法整段注释掉，重启，发送 6.1——BusinessException 没人认领时会发生什么？（观察：Spring 的默认兜底返回什么格式。）看完把注释还原。
2. **加一种客诉**：字典里加 `DISH_SOLD_OUT(40402, "这道菜今天卖完了")`，在点单循环里加一个判断：菜名是"麻婆豆腐"就抛这个异常（模拟售罄），验证信封和前端提示。做完还原。
3. **思考题**：现在出错时 HTTP 状态码也是 200，只靠 `code` 区分。支持者说"业务错误不是 HTTP 意义上的失败"；反对者说"网关、监控、浏览器都认状态码，全 200 会骗过它们"。你怎么看？（提示：真实世界两种都有，Spring 提供 `ResponseEntity` / `@ResponseStatus` 让你能精确控制状态码——本课程保持 200+业务码，知道另一派的存在即可。）

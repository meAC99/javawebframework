# 第6课 · 课程导入：全店统一客诉处理台

## 上一课发生了什么

成功时，所有接口都回统一的 `Result` 信封了。可失败时呢？你重放一下 2.3 佛跳墙：状态码 500，响应体还是一段机器味的报错：

```json
{"timestamp":"2026-09-06T...","status":500,"error":"Internal Server Error","path":"/order"}
```

顾客点错一道菜，得到的是"Internal Server Error"——像后厨直接把锅铲扔到了客人桌上。而且这还不是最糟的：**报错格式没有规矩**。`/order` 抛这种 500，`/menu` 假如出错抛另一种，前端每接一个接口就要猜一次"错长什么样"。

## 今天要建的：客诉处理台

真实饭店怎么处理客诉？不管哪个环节出的错，最后都由**大堂经理**出面：先判断是顾客的问题还是店的问题，再按规矩回话——"这道菜本店没有"（业务问题，微笑道歉）还是"厨房设备故障"（系统事故，马上抢修并记入值班日志）。

今天你写的 `GlobalExceptionHandler` 就是这位大堂经理。从此：

- **任何接口**抛出的**任何异常**，都由它统一转成 `Result` 信封
- 业务问题（点错菜）和系统事故（程序炸了）**分流处理、分流记日志**（warn vs error）
- 连第 1 课就见过的"404 + timestamp"报错，也会被它接住换成规范信封

```
改造前：/order 抛 RuntimeException → 框架默认处理 → 500 + timestamp JSON
改造后：任何异常 → GlobalExceptionHandler → {code, msg, data} 信封 + 分级日志
```

## 本课你将学会

1. `@RestControllerAdvice` + `@ExceptionHandler`：一个类兜住全店所有接口的异常
2. 自定义业务异常 `BusinessException`：携带错误码往上抛
3. 三级分流：业务异常（warn）→ 路径不存在（404 类）→ 系统异常（error 兜底）
4. 日志分级：`log.warn` 与 `log.error` 的使用场景

## 先想清楚一个问题：异常抛出去之后，去哪了？

第 2 课你写了 `throw new RuntimeException("菜品不存在：佛跳墙")`，从没写过 try-catch 去接它——它去哪了？

答案是**一路向上抛**：`order()` 方法没有 catch → 抛给 Spring MVC 的调度器 → 调度器也没有接的处理逻辑 → 最后交给 Servlet 容器（Tomcat）默认错误页机制 → 于是顾客看到了 500。

本课做的事，就是在"调度器"这一层安插一个人：`@RestControllerAdvice` 告诉 Spring——"所有 Controller 抛出的异常，都先送到我这里来"。**你不需要在每个方法里 try-catch，异常只管往上抛，终点有专人接。**

另外一个设计问题：业务异常为什么继承 `RuntimeException`（运行时异常）而不是普通 `Exception`？两个理由：① 调用方不必强制 try-catch，代码干净；② Spring 事务默认只回滚 RuntimeException——这个理由现在先记下，第 11 课你会亲眼验证它的分量。

# 第13课 · 课程导入：菜品拍照上架

## 上一课发生了什么

账本阶段收官：菜单、订单、明细全在数据库里，事务兜底，翻账有分页。但老板打开点餐网页端详半天，说了句大实话——**"全是文字，看着不馋。"**

美团时代的人看菜单，先看图。今天起进入"照片与会员"阶段，第一件事：**给菜品传照片**。

## 今天的第一个新世界：请求体不止 JSON

前面 12 课，POST 请求的请求体清一色 JSON（`@RequestBody`）。但传文件不是 JSON 能干的活——一张照片几 MB 的二进制，套成 JSON 会膨胀体积还得转码。业界标准是 **`multipart/form-data`（多部件表单）**：

```
------boundary（分界线）
Content-Disposition: form-data; name="file"; filename="huiguorou.png"
Content-Type: image/png

（图片的二进制内容）
------boundary--
```

一个请求体被"分界线"切成几段，每段自带小头部——文件、普通表单字段可以混着传。你不用手工拼这些，Spring 给你一个容器类 **`MultipartFile`**：文件名、大小、内容流，全帮你解析好。

## 今天的第二个重点：接口先行的设计（埋一颗第 19 课的种子）

"存文件"这件事有不止一种做法：今天存**本地磁盘**；第 19 课换**MinIO 对象存储**（docker 里的文件服务器）。如果上传代码直接写死"存本地"，换存储时就要到处改。

所以今天的写法是：先定义接口 `StorageService`（**只说"存文件"这个能力，不说存在哪**），再写本地实现 `LocalStorageService`。用的时候面向接口——第 19 课新增一个 MinIO 实现，**业务代码一行不改**。这就是第 4 课"@Autowired 注入的是类型"埋下的伏笔：注入接口，实现随配随换。

## 本课你将学会

1. `MultipartFile` 接收 multipart 上传，REST Client 怎么发这种请求

## 先想清楚：为什么不能信任用户上传的原始文件名？

用户上传的 `filename` 是请求里带来的字符串，**想写什么写什么**：起名 `../pom.xml` 可能覆盖你的项目文件；起名 `evil.jpg` 内容却是可执行脚本。所以本课实现的规矩是：**原始文件名只取它的扩展名（且必须过白名单），新文件名一律用服务端生成的 UUID**——用户说了不算，服务端说了算。

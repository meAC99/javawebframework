# 第9课 · 动手做：一对多实体 + 收银台 + 服务员瘦身

共 5 步。两个新实体、一个新 Repository、一个新 Service，外加服务员史上最大的一次瘦身。

## Step 1：订单本实体 Order（20 分钟）

新建 `entity/Order.java`：

```java
package com.cdutetc.nanpo.entity;

import java.math.BigDecimal;
import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;

import lombok.Data;
import lombok.EqualsAndHashCode;
import lombok.NoArgsConstructor;
import lombok.ToString;

/**
 * 订单实体（订单主表）。
 * 表名用 t_order：order 是 SQL 保留字（ORDER BY 的 ORDER），直接用会语法报错。
 *
 * 一对多的"一方"：mappedBy 表示关系由对方（OrderItem 的 order 字段）维护，
 * 不会额外生成中间表；cascade=ALL 让保存订单时明细一并入库。
 */
@Entity
@Table(name = "t_order")
@Data
@NoArgsConstructor
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private BigDecimal totalAmount;

    private LocalDateTime createTime;

    // 双向关联里 lombok 的 toString/equals 会沿着 order→items→order 互相调用，
    // 不排除会无限递归——两个 @xxxExclude 是规矩写法
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    @ToString.Exclude
    @EqualsAndHashCode.Exclude
    private List<OrderItem> orderItems = new ArrayList<>();

    // 双向关联辅助方法：两边同时赋值，外键 order_id 才能正确回填
    public void addOrderItem(OrderItem item) {
        orderItems.add(item);
        item.setOrder(this);
    }
}
```

四个关键点：

- **表名 `t_order`**：试试建表叫 `order`，SQL 直接语法错——`ORDER` 是保留字（`ORDER BY`）。
- **`mappedBy = "order"`**：告诉 JPA"关系由对方的 order 字段维护"。有了它，只建两张表 + 一个外键列；**没有它**会多出一张中间关联表（不是我们要的）。记忆：`mappedBy` 在哪边，哪边就是"被维护方"（一方）。
- **`cascade = CascadeType.ALL`**：级联——保存 Order 时，orderItems 里的明细**自动跟着保存**，不用循环逐条 save。本课 Step 4 一行 `save(order)` 落两张表，靠的就是它。
- **`addOrderItem()` 辅助方法**：双向引用最怕"只挂一边"（订单记得明细、明细不记得订单 → 外键是 null）。这个方法保证两边同时赋值——**用它的订单，外键才正确**。

## Step 2：明细页实体 OrderItem（15 分钟）

新建 `entity/OrderItem.java`。**注意包名**：它在 entity 包，和 pojo 包里第 2 课的小票类 `OrderItem` 同名——这个冲突是故意的，Step 4 你会亲身体会它的别扭（第 10 课的导火索）：

```java
package com.cdutetc.nanpo.entity;

import java.math.BigDecimal;

import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

import lombok.Data;
import lombok.EqualsAndHashCode;
import lombok.NoArgsConstructor;
import lombok.ToString;

/**
 * 订单明细实体（订单明细表）：一单多个菜，每个菜一行。
 *
 * 一对多的"多方"：外键列 order_id 定义在这一侧（@JoinColumn）；
 * LAZY 懒加载——查明细时才顺带取订单，不主动查就不发 SQL。
 */
@Entity
@Table(name = "t_order_item")
@Data
@NoArgsConstructor
public class OrderItem {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id", nullable = false)
    @ToString.Exclude
    @EqualsAndHashCode.Exclude
    private Order order;

    private String dishName;

    private Integer count;

    /** 价格快照：下单那一刻的菜单价。之后菜单调价，历史订单金额不变。 */
    private BigDecimal unitPrice;

    private BigDecimal subTotal;

    // 不用 @AllArgsConstructor（它会带上 id 和 order），手写业务用得上的四参构造器
    public OrderItem(String dishName, Integer count, BigDecimal unitPrice, BigDecimal subTotal) {
        this.dishName = dishName;
        this.count = count;
        this.unitPrice = unitPrice;
        this.subTotal = subTotal;
    }
}
```

看懂"多方"的三个注解：

- `@ManyToOne` + `@JoinColumn(name = "order_id")`：外键列定义在**这一侧**（和 `mappedBy` 正好配套）。`nullable = false`：明细必须属于一张订单。
- `fetch = FetchType.LAZY`：懒加载——`order` 字段默认不查库，真用到才发 SQL。多表关联的默认性能保护。
- 又见 `@ToString.Exclude`：两边都排除，toString/equals 才不会互相调用打穿栈。

## 插曲：这两个实体的新注解，一次讲透

两个类写完了，但里面一口气出现了 **7 个以前没见过的注解** 和 **1 个奇怪的辅助方法**。它们是一对多关联的完整工具箱——逐个掰开（下面的解释都拿"1 号订单 + 回锅肉明细"当例子）。

### 0. 先建立一张全景图

```
Order（订单本，一方）                        OrderItem（明细页，多方）
┌─────────────────────────┐                ┌──────────────────────────┐
│ @OneToMany(mappedBy="order")             │ @ManyToOne(fetch=LAZY)
│   ├─ cascade=ALL          │◀───镜像视图───│ @JoinColumn(name="order_id")
│   └─ orphanRemoval=true   │              │   └─ nullable=false
│ orderItems: List<Item>   │  ──真正维护──▶ │ order: Order
└─────────────────────────┘    (外键在这边) └──────────────────────────┘
        addOrderItem(item)  ←──── 把两边同时挂上的"接线员"
```

一句话总纲：**外键列 `order_id` 住在多方（OrderItem），所以多方是"关系的主人"；一方（Order）的 `orderItems` 只是一个由主人同步过来的"成员名单"（镜像）。** 下面每个注解都是围绕这个主从关系服务的。

### 1. `@OneToMany(mappedBy = "order")`——一方"甩手不管"

- **写的是什么**：`"order"` 是**对方类里指向我的字段名**——OrderItem 里的 `order` 字段。它不是表名、不是列名，是 Java 字段名，拼错直接启动报错。
- **含义**："本方不管关系，关系的真实数据（外键）由对方那个字段维护。" 于是建表只出**两张表 + 一个外键列**，正是我们画的图。
- **不写会怎样**：JPA 认为两边都在管关系，只好生成**第三张中间表**（类似 `t_order_order_items`，存两边的 id）——三张表、多一次 join，不是我们要的结构。
- 记法：**mappedBy 在哪边，哪边就甩手**（一方甩手，多方管账）。

### 2. `@ManyToOne` + `@JoinColumn(name = "order_id")`——主人亮出外键

- `@ManyToOne`：多个明细指向同一个订单（N : 1）。挂在**外键所在的字段**上——`private Order order;` 这个字段就是数据库里 `order_id` 列在 Java 里的化身。
- `@JoinColumn(name = "order_id")`：明确外键**列名**。不写的话默认叫 `order_id`（实体名+id），显式写出来是为了看得见、改得名。
- `nullable = false`：建表时自动带 `NOT NULL`——孤儿明细（不属于任何订单的菜）在数据库层面就不允许存在。
- 对照建出来的 SQL 记忆：

```sql
CREATE TABLE t_order_item (
    ...
    order_id BIGINT NOT NULL,
    FOREIGN KEY (order_id) REFERENCES t_order(id)
);
```

### 3. `fetch = FetchType.LAZY`——懒加载，要用再查

- 两种取数策略：**EAGER（立即）**——查这个对象时，关联对象**马上**再发一条 SQL 一起查回来；**LAZY（懒惰）**——先只给你一个"欠条"，真访问关联对象的属性那一刻才发 SQL。
- **一个容易反直觉的事实**：JPA 的默认值是——`@ManyToOne` 默认 **EAGER**、`@OneToMany` 默认 LAZY。所以我们显式写 `LAZY`，是把多方的默认值改掉。
- **为什么查明细要懒**：设想翻 100 条明细，如果 EAGER，查每条都顺带把订单查一遍——而订单每次都是同一个！100 次浪费。LAZY 让"不碰 order 就不发 SQL"。
- 本课的实证就在动手做 Step 4 的厨房循环里：`for (OrderItem item : saved.getOrderItems())` 只读了 item 自己的字段（`getDishName()/getCount()`），日志里**没有**为每个 item 再发一条查订单的 SQL——懒加载在省钱。

### 4. `cascade = CascadeType.ALL`——我的操作，明细跟班

- **级联（cascade）**：对 Order 做某操作时，`orderItems` 里的对象自动做同样操作。`ALL` 是全家桶（PERSIST、MERGE、REMOVE、REFRESH……）。
- **本课真正用到的是 PERSIST**：`orderRepository.save(order)` 一行，Hibernate 遍历 orderItems 把每个明细也 insert——验证清单里的"insert 三连"（1 条订单 + 2 条明细）就是它的作品。**没有 cascade，save 只存订单，明细得自己循环 save。**
- **REMOVE 的另一面**（本课不触发，但要心里有数）：删订单会连着删所有明细——"整单作废"语义。思考题 3 会让你掂量这件事的危险性。

### 5. `orphanRemoval = true`——孤儿清除

- **孤儿**：从 `orderItems` 列表里被移除、不再属于任何订单的明细。它失去了存在意义（一个"回锅肉明细"离开订单什么都不是），`orphanRemoval=true` 让数据库里这行也删掉。
- **和 cascade REMOVE 的分工**：cascade 管"整单删除"（连锅端），orphanRemoval 管"从名单里剔除单项"（点错了撤一道菜）。两者合起来，`orderItems` 这个列表才真正"说了算"。

### 6. `@ToString.Exclude` / `@EqualsAndHashCode.Exclude`——剪断 lombok 的死循环

- `@Data` 会替你生成 `toString()` 和 `equals()`，默认**把所有字段**打进去/比一遍——包括互相指向的关联字段。
- 于是环出现了：

```
order.toString()          要打印 orderItems
  └─ item.toString()        要打印它的 order
       └─ order.toString()    又要打印 orderItems
            └─ ……（无限递归 → StackOverflowError）
```

- `@ToString.Exclude`：生成 toString 时跳过该字段；`@EqualsAndHashCode.Exclude`：equals/hashCode 同理。**排除任意一侧就能剪断环**——环是两边一起构成的，断一处即断；**两边都排**是更稳的惯用法：无论从哪一端打印/比较都干净对称，将来谁改掉另一边也不怕（课后练习 4 让你两种情况都亲眼看看）。
- 想亲眼看看不排的下场？课后练习 4 安排了这个实验。

### 7. `addOrderItem()`——为什么出现，谁在调用？

**为什么需要它——外键回填的底层机制**。`save(order)` 时，Hibernate 写明细的 insert 语句，`order_id` 列的值从哪读？从**明细对象自己的 `order` 字段**读（回想第 1 点：外键的主人在多方）。于是：

```
挂接前的内存（危险状态）：
order ──orderItems──▶ [item]        order 记得 item
item ──order──▶ null                item 不记得 order ✗

save 时：insert into t_order_item (..., order_id, ...) values (..., ???, ...)
                                                ↑ item.order 是 null → 写入 null → 违反 NOT NULL，报错！
```

所以**两边必须同时挂**：

```
挂接后（addOrderItem 做的事）：
order ──orderItems──▶ [item] ◀──order── 双向打通 ✓
save 时：order_id 从 item.order 读到订单 → 正确回填（验证清单里明细行有 order_id=1 的原因）
```

**为什么不让大家手写两行，而要封装成方法**：`order.getOrderItems().add(item)` 和 `item.setOrder(order)` 分开写，总有一天有人只写一半（单边挂接）——编译不报错、跑起来才炸，是最阴的 bug。封装成一个方法，调用方**不可能**忘记另一半。这和第 6 课"统一异常"、第 8 课"幂等初始化"是同一种工程思维：**把容易做错的事，做成容易做对的事。**

**谁在调用它**：Step 4 的 `OrderService.createOrder` 循环里——

```java
order.addOrderItem(new OrderItem(dishName, count, menu.getPrice(), subTotal));
```

每验过一道菜就 new 一个明细并挂上订单；循环结束 `save(order)`，级联+外键回填一起生效。**你永远不会在别处看到"item.setOrder(order)"散落在外**——都从这个方法走。

## Step 3：OrderRepository——本课一行方法都不用写（5 分钟）

新建 `dao/OrderRepository.java`：

```java
package com.cdutetc.nanpo.dao;

import org.springframework.data.jpa.repository.JpaRepository;

import com.cdutetc.nanpo.entity.Order;

/**
 * 订单的数据访问接口。
 * 明细（t_order_item）靠 Order 上的 cascade=ALL 级联保存，
 * 所以暂时不需要单独的 OrderItemRepository。
 */
public interface OrderRepository extends JpaRepository<Order, Long> {
}
```

空的接口？不空——`JpaRepository` 白送的 `save/findById/findAll/count` 已经够用，明细全靠级联带着走。**能在框架里少写的就是不用写的**。

## Step 4：收银台 OrderService + 服务员瘦身（25 分钟）

新建 `service/OrderService.java`——从今天起，下单的全部业务住在这里：

```java
package com.cdutetc.nanpo.service;

import java.math.BigDecimal;
import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;

import org.springframework.stereotype.Service;

import com.cdutetc.nanpo.common.BusinessException;
import com.cdutetc.nanpo.common.ErrorCodeEnum;
import com.cdutetc.nanpo.dao.MenuRepository;
import com.cdutetc.nanpo.dao.OrderRepository;
import com.cdutetc.nanpo.entity.Menu;
import com.cdutetc.nanpo.entity.Order;
import com.cdutetc.nanpo.pojo.OrderItem;
import com.cdutetc.nanpo.pojo.OrderRequest;
import com.cdutetc.nanpo.pojo.OrderResponse;

/**
 * 收银台（订单业务服务）。
 * 第9课新增：服务员身上"验菜算价、编排厨房、订单落库"的全部业务搬到这里——
 * Controller 只管 HTTP 进出，业务编排属于 Service 层。
 */
@Service
public class OrderService {

    private final MenuRepository menuRepository;
    private final OrderRepository orderRepository;
    private final SideDishService sideDishService;
    private final CookService cookService;

    // 构造器注入：第8课在 MenuDataInitializer 里示范过，本次推广为常规写法
    public OrderService(MenuRepository menuRepository,
                        OrderRepository orderRepository,
                        SideDishService sideDishService,
                        CookService cookService) {
        this.menuRepository = menuRepository;
        this.orderRepository = orderRepository;
        this.sideDishService = sideDishService;
        this.cookService = cookService;
    }

    public OrderResponse createOrder(OrderRequest request) {
        Order order = new Order();
        order.setCreateTime(LocalDateTime.now());
        BigDecimal total = BigDecimal.ZERO;

        // 小票侧：给前端看的明细（第2课以来的 pojo.OrderItem）
        List<OrderItem> receiptItems = new ArrayList<>();

        for (OrderRequest.DishCount dc : request.getDishList()) {
            String dishName = dc.getDishName();
            Integer count = dc.getCount();

            // 验菜+取价（第8课已改为查库）
            Menu menu = menuRepository.findByDishName(dishName)
                    .orElseThrow(() -> new BusinessException(ErrorCodeEnum.DISH_NOT_FOUND));

            BigDecimal subTotal = menu.getPrice().multiply(BigDecimal.valueOf(count));
            total = total.add(subTotal);

            // 账本侧：明细实体挂上订单（unitPrice 是价格快照）。
            // 注意这里必须写全限定名：entity.OrderItem 与 pojo.OrderItem 同名，
            // 同一个文件里 import 不了两个——这个别扭正是第10课
            // "小票与账本分离(DTO/VO)"要解决的
            com.cdutetc.nanpo.entity.OrderItem item =
                    new com.cdutetc.nanpo.entity.OrderItem(dishName, count, menu.getPrice(), subTotal);
            order.addOrderItem(item);

            // 小票侧：并行拼一份前端明细
            OrderItem receiptItem = new OrderItem();
            receiptItem.setDishName(dishName);
            receiptItem.setCount(count);
            receiptItem.setUnitPrice(menu.getPrice());
            receiptItem.setSubTotal(subTotal);
            receiptItems.add(receiptItem);

            // 厨房编排（第3课的调用链从 Controller 搬进业务层）
            sideDishService.prepareSideMaterial(dishName, count);
            cookService.cookDish(dishName, count);
        }

        order.setTotalAmount(total);
        // cascade=ALL：一次 save，主表明细全部入库，order_id 自动回填
        Order saved = orderRepository.save(order);

        OrderResponse resp = new OrderResponse();
        resp.setItemList(receiptItems);
        resp.setTotalMoney(saved.getTotalAmount());
        // 带上数据库生成的订单号——前端肉眼可见"真的入库了"
        resp.setMsg("下单成功，请到取餐口稍等～（订单号 " + saved.getId() + "）");
        return resp;
    }
}
```

**亲身体会那个别扭**：`entity.OrderItem` 和 `pojo.OrderItem` 同名，一个 Java 文件里 import 了 `pojo.OrderItem`，实体那边就只能写全限定名 `com.cdutetc.nanpo.entity.OrderItem`——能跑，但丑，而且每次读这行都硌眼。**记住这个不爽**，第 10 课你会亲手消灭它。

**留意"两套对象并行拼"**：循环里同时维护账本侧（实体）和小票侧（pojo）两份明细——同一个数据抄两遍，也是个坏味道。第 10 课一起解决。

然后给服务员瘦身——`WaiterController.java`：

- **删掉** `sideDishService`、`cookService` 两个注入和整个 `order()` 方法体（几十行业务）
- **新增** `@Autowired private OrderService orderService;`
- `/order` 变成一行转发：

```java
    // 点单：对照第2课——那时这里堆着几十行验菜算账炒菜的业务代码，
    // 现在只剩"转交给收银台"一行。业务逻辑放 Service 层，
    // Controller 可测试、可替换，将来 AI 点单（第18课）也能复用同一个收银台
    @PostMapping("/order")
    public Result<OrderResponse> order(@RequestBody OrderRequest orderRequest) {
        return Result.success(orderService.createOrder(orderRequest));
    }
```

`/menu` 不动。类头注释追加：`第9课：服务员瘦身——下单的全部业务搬进 OrderService（收银台）…`。对照第 2 课：这个类从 78 行的"全能服务员"，瘦成了纯转发的"传菜员"。

# 第9课 · 课程导入：订单落库（订单本 + 明细页）

## 上一课发生了什么

菜谱搬进了 `t_menu`，改价不用发版了。但 `/order` 点完单，算好的订单**哪儿都没存**——数据在响应里走一圈就消失了。重启全没、无法对账、没法统计"今天回锅肉卖了几份"。你的店记账只记菜单，不记生意。

今天给订单建账。先想一个设计问题：

> 一张订单 = 订单头（单号、总额、时间）+ N 行明细（菜名、数量、单价、小计）。
> 为什么不做成一张"宽表"——一行存完一整张订单（菜1、菜2、菜3……各来一列）？

宽表的死穴一眼可见：点 3 个菜和点 8 个菜的订单长不一样，要么浪费大量空列，要么列不够用。正确解法是**两本账、一对多**：

```
t_order（订单本：一本一条）          t_order_item（明细页：一菜一行）
├─ id          主键                 ├─ id          主键
├─ total_amount 总额                ├─ order_id    外键 → 指向订单本 ★
└─ create_time 下单时间             ├─ dish_name / count
                                    ├─ unit_price  价格快照 ★
                                    └─ sub_total
```

两个带 ★ 的设计是本课的灵魂：

- **外键 `order_id`**：每行明细记得自己属于哪张订单——多与多的关系靠它连起来。
- **价格快照 `unit_price`**：存"下单那一刻"的菜单价。以后菜单调价，**历史订单的金额不许变**——这是订单系统的行业铁律（不然上个月的账这月就对不上了）。

## 先想清楚：为什么"一对多"会让 Java 对象互相引用？

表的世界里，明细靠一个 `order_id` 列挂到订单上；而 Java 对象的世界里没有"外键"这种东西，靠的是**你引用我、我引用你**：

```
Order ──orderItems──▶ List<OrderItem>     （订单知道自己的明细们）
OrderItem ──order──▶ Order                （明细知道自己属于哪张订单）
```

双向引用好用，但暗藏杀机：lombok 生成的 `toString()` 会沿着引用一路打进去——Order 打 items、每个 item 又打回 Order……**无限递归，栈溢出**。本课的实体代码里你会看到防御写法。

> **预习地图**：本课实体代码里会一口气出现 **7 个新注解**（`mappedBy`、`cascade`、`orphanRemoval`、`@JoinColumn`、`LAZY`、两个 `Exclude`）和 **1 个 `addOrderItem()` 辅助方法**——每个是干嘛的、为什么出现、谁会调用，动手做文件里"**插曲：这两个实体的新注解，一次讲透**"一节有完整展开（配内存图）。写到 Step 2 之后**别跳过它**，后面十课都要靠这些地基。

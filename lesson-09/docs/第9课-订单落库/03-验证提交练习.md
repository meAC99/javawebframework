## 一、验证清单（全过才算下课）

**1. 重放 2.2 正常点单——小票带上了订单号**

预期：

```json
{"code":200,"data":{"itemList":[{"count":2,"dishName":"回锅肉","subTotal":36.00,"unitPrice":18.00},{"count":2,"dishName":"米饭","subTotal":2.00,"unitPrice":1.00}],"msg":"下单成功，请到取餐口稍等～（订单号 1）","totalMoney":38.00},"msg":"操作成功"}
```

`（订单号 1）`——这个 `1` 不是你写的，是数据库自增主键。它出现在小票上，就证明订单真的入库又取回来了。

**2. 看"透视眼"：落库三连**

刚才那次请求，终端按顺序打出：

```
Hibernate: insert into t_order (create_time,total_amount,id) values (?,?,default)
Hibernate: insert into t_order_item (count,dish_name,order_id,sub_total,unit_price,id) values (?,?,?,?,?,default)
Hibernate: insert into t_order_item (...) values (?,?,?,?,?,default)     ← 第二道菜
```

读出三个信息：先订单后明细（级联的顺序）；明细 insert 里的 `order_id` 列有值（`addOrderItem` 的功劳）；**你只写了一行 `save(order)`**（cascade 的功劳）。

**3. h2-console 亲眼验证两本账**

```sql

SELECT * FROM T_ORDER_ITEM;
```

预期：订单本 1 行（`TOTAL_AMOUNT=38.00`）；明细页 2 行，每行的 `ORDER_ID` 都是 1——外键把两本账缝在了一起。

**4. 厨房调用链搬家后的回归**

终端应照常打出 `[墩子] 回锅肉 x 2 配菜完成` → `[厨师] 回锅肉 x 2 炒菜完成`——调用链从 Controller 搬进 OrderService，一次都没断。

## 三、课后练习

1. **价格快照实验（本课灵魂，必做）**：在 h2-console 执行 `UPDATE T_MENU SET PRICE = 25 WHERE DISH_NAME = '回锅肉';`，重放 2.2 再下一单。然后 `SELECT DISH_NAME, UNIT_PRICE FROM T_ORDER_ITEM;`——老订单的回锅肉还是 18.00，新订单是 25.00。**菜单调了价，历史订单纹丝不动**，这就是价格快照。做完把价格改回 18。
2. **画一次调用链**：拿出纸，画出这次 POST /order 从浏览器到数据库再回来的完整链路（Controller → OrderService → MenuRepository / OrderRepository → 墩子 → 厨师）。第 3 课的调用链现在长什么样了？
3. **思考题**：`cascade = CascadeType.ALL` 意味着删订单时明细也会被删（orphanRemoval）。什么场景这是好事？什么场景是灾难？（提示：订单能随便删吗？——"删除"在真实业务里往往用状态字段代替，第 16 课的订单记名会再次涉及。）
4. **亲眼见一次死循环（配合"插曲"第 6 条，两阶段实验）**：
   **阶段一**：只把 `Order` 里的 `@ToString.Exclude` 临时注释掉，在 `createOrder` 的 `save` 之后加一行 `System.out.println(order);`，重启下一单——**不炸**，正常打印（明细列表可见；递归走到 item 那层被它自己的 Exclude 拦住了）——断一处即断环。
   **阶段二**：把 `OrderItem` 里的 `@ToString.Exclude` 也注释掉，再下一单——控制台 `StackOverflowError`，异常栈里 `toString` 的帧影一层压一层。
   结论自现：**排除任意一侧即断环；两边都排是惯例保险。** 做完把两处注释和临时代码全部还原再提交。

## 四、下一课预告

订单落库了，但今天的代码留了两个坏味道，你自己都能感觉到：

1. `entity.OrderItem` 和 `pojo.OrderItem` 同名打架，只能写全限定名，丑；
2. 循环里"账本"和"小票"两套对象并行拼一遍，同一份数据抄两遍。

更危险的是一个问题还没爆：**如果哪天有人直接把 Order 实体返回给前端，会发生什么？** 双向引用 Order→items→每个 item 又指回 Order……下一课开场你就亲手引爆它，然后用"小票与账本分离"（dto/vo/entity 三层对象各司其职）一次性解决这三个问题。第 2 课出生的 `pojo` 包，也将在那一课光荣退役。
